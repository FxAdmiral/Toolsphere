Databases for Beginners: Tables, SQL and Keeping Data Safe

What is a database?

A database is an organised collection of data that a program can store, search and update quickly. You could keep data in plain files, but a database handles many users at once, finds records fast, keeps data consistent and protects it from being half-saved if something crashes.

Almost every application uses one: your account details, your messages, a shop's products, a blog's articles.

The two main families

  • Relational (SQL) databases store data in tables made of rows and columns, a bit like spreadsheets that can be linked together. Examples: PostgreSQL, MySQL and SQLite.
  • Document databases store flexible, JSON-like documents. Example: MongoDB.

Neither is better in every case. Relational databases suit structured data with clear relationships, such as customers and orders. Document databases suit data whose shape varies or changes often.

Tables, rows, columns and keys

  • A table holds one kind of thing, such as users.
  • A column is one property, such as email.
  • A row is one record, such as one user.
  • A primary key is a column whose value is unique for every row, usually an id.
  • A foreign key is a column that points to a row in another table, which is how tables are linked.

SQL basics

SQL (Structured Query Language) is the language for talking to relational databases. These examples use SQLite style. 

CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE
);

INSERT INTO users (name, email) VALUES ('Ada', 'ada@example.com');
INSERT INTO users (name, email) VALUES ('Tunde', 'tunde@example.com');

SELECT id, name FROM users WHERE name = 'Ada';

UPDATE users SET email = 'ada.new@example.com' WHERE id = 1;

DELETE FROM users WHERE id = 2;
  • CREATE TABLE defines a table and its columns.
  • INSERT adds a row.
  • SELECT reads rows, and WHERE filters them.
  • UPDATE changes rows. DELETE removes them.
Always use WHERE with UPDATE and DELETE. Without it, the command changes or deletes every row in the table.

Small details of SQL differ between database systems. For example, the way to make an automatically numbered id is not the same in PostgreSQL as in SQLite. The core ideas stay the same.

Relationships and JOIN

A user can have many orders. Instead of copying the user's details into every order, store the user's id in the order, and use a JOIN to combine them when you read the data: 

CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    item TEXT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

INSERT INTO orders (user_id, item) VALUES (1, 'Notebook');

SELECT users.name, orders.item
FROM orders
JOIN users ON users.id = orders.user_id;

A quick look at a document database

The same kind of information as one document:

{
  "_id": "u1",
  "name": "Ada",
  "skills": ["HTML", "CSS"],
  "address": { "city": "Lagos" }
}

Related data, such as skills and address, can sit inside the document. That is convenient when you usually read it all together.

Keeping data safe

  • Prevent SQL injection. Never build a query by joining user text into it. Use parameterised queries, where the database receives the value separately and treats it only as data.
// UNSAFE: user text is glued into the query
db.query("SELECT * FROM users WHERE email = '" + email + "'");

// SAFE: the value is passed separately as a parameter
db.query("SELECT * FROM users WHERE email = ?", [email]);

(The placeholder style differs between libraries. Some use ? and others use $1.)

  • Never store plain passwords. Store a hash made by a dedicated password-hashing method such as Argon2id, bcrypt or scrypt. A plain SHA-256 hash from our Hash Generator is not enough for passwords.
  • Keep credentials out of your code. Put the database password in an environment variable, keep the .env file out of Git, and replace the password at once if it is ever exposed.
  • Give each program only the access it needs. A website that only reads data should not be able to delete tables.
  • Make backups, and test that you can restore them.

Which one should you choose?

  • SQLite: a whole database in a single file with no server to run. Excellent for learning and small projects.
  • PostgreSQL: a powerful, widely used relational database for serious applications.
  • MongoDB: a good fit when your data is naturally document-shaped.

Pick the simplest option that fits your data. You can always move later, though moving is work.

Where databases fit in ToolSphere

ToolSphere's current tools need no database, because they run in your browser and store nothing. A database will make sense when we add features that must remember things, such as saved contact messages or article management.

Common beginner mistakes

  • Running UPDATE or DELETE without WHERE.
  • Storing several values in one column, such as a comma-separated list, instead of using a related table.
  • Trusting user input in a query.
  • Storing passwords or secrets in plain text.
  • Having no backup.

Practice project

Install SQLite, or use the sqlite3 command if your system already has it. Run the SQL from this guide, then add a products table with a name and a price, insert five rows, and write queries to find products under a chosen price and to list them from the cheapest to the most expensive (hint: ORDER BY).

Summary

  • A database stores data so programs can find and update it reliably.
  • Relational databases use tables and SQL. Document databases use flexible documents.
  • Primary keys identify rows, and foreign keys link tables.
  • Use parameterised queries, hash passwords properly and keep credentials secret.
  • Choose the simplest database that fits.
