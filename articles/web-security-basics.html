What is the OWASP Top 10?

OWASP (the Open Worldwide Application Security Project) is a non-profit community that publishes free security knowledge. Its best known document, the OWASP Top 10, lists the most serious and common weaknesses in web applications. It is updated every few years, so check owasp.org for the newest edition. This guide explains the ideas in plain language and, as defence, what to do about each.

The categories in the 2025 edition are listed below. The names may be reworded in later editions, but the underlying problems are long-lived.

1. Broken access control

A user can do something they should not be allowed to do, such as view another person's order by changing a number in the address. The server must check every request, not just hide buttons. 

// Weak: trusts the id in the URL
app.get("/orders/:id", (req, res) => {
    res.json(getOrder(req.params.id));
});

// Better: also checks the order belongs to the signed-in user
app.get("/orders/:id", (req, res) => {
    const order = getOrder(req.params.id);

    if (!order || order.userId !== req.user.id) {
        return res.status(404).send("Not found");
    }

    res.json(order);
});

2. Security misconfiguration

Unsafe settings: default passwords left unchanged, debug pages left on, unnecessary services running, or storage left open to the public. Defence: use a secure baseline, remove what you do not need, and review settings regularly.

3. Software supply chain failures

Your project depends on code written by others, and so do they. A compromised or malicious package can end up in your site. Defence: use few dependencies, trusted sources, lock files and regular updates, and run npm audit or similar checks.

4. Cryptographic failures

Sensitive data sent or stored without proper protection, or with weak or home-made cryptography. Defence: use HTTPS everywhere, store passwords with Argon2id, bcrypt or scrypt, and use well-tested libraries. Read Why Base64 Isn't Encryption to see why encoding is not protection.

5. Injection

Untrusted input is mixed into a command or query and treated as instructions. SQL injection and cross-site scripting (XSS) are the best known. Defence: keep data separate from commands. Use parameterised queries (see the Databases guide) and treat page content as text: 

// Risky: the text is treated as HTML
output.innerHTML = userText;

// Safer: the text is treated only as text
output.textContent = userText;

6. Insecure design

The problem is in the plan, not the code, such as a password reset that anyone can abuse. Defence: think about how things could be misused while designing, and not only after building.

7. Authentication failures

Weak sign-in: guessable passwords allowed, no limit on attempts, poor session handling. Defence: require strong passwords (the Password Strength Checker shows what weakness looks like), limit login attempts, offer multi-factor authentication and expire sessions properly.

8. Software or data integrity failures

Trusting code or data without checking that it is genuine, for example loading a script from an unverified source or accepting unsigned updates. Defence: verify sources and signatures, and protect your build and update process.

9. Security logging and alerting failures

Without good logs and alerts, attacks go unnoticed for weeks. This links straight to the SOC guides: Logs, Alerts and SIEM. Defence: log sign-ins and important actions, protect the logs, and make sure someone is alerted.

10. Mishandling of exceptional conditions

Errors and unusual situations handled badly: crashes that expose internal details, or code that "fails open" and lets people in when something goes wrong. Defence: handle errors deliberately, show users a friendly message, keep details in your logs, and make failures safe by default.

Helpful security headers

Web servers can send headers that tell browsers to behave more safely. Check each one before use, because a strict policy can break a page: 

Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin

Habits of a secure developer

  • Never trust input from a browser. Validate it on the server.
  • Give every account and program the least access it needs.
  • Keep software and dependencies updated.
  • Keep secrets out of code and out of Git.
  • Log important events and review them.

Common beginner mistakes

  • Checking permissions only in the front end.
  • Showing detailed error messages to visitors.
  • Trusting a package because it has a nice README.
  • Treating the Top 10 as a complete checklist. It is a starting point.

Practice project

Take one of the small pages or Express servers you built in the programming guides. For each of the ten categories, write one sentence on whether it applies and one change that would make the project safer. Make the changes you can.

Summary

  • The OWASP Top 10 lists the most common web application weaknesses.
  • Check access on the server, keep data separate from commands, and protect secrets.
  • Use HTTPS, strong password storage, updates and careful dependencies.
  • Log, alert and handle errors safely.
